# Declarative

DSL is declarative. Each action asserts a state that should exist. Actions are not functions that run code but prove that the desired outcome is valid. This is akin to Elixir's match operator (=) in that it is not an instruction for work, and actions can be thought of in Elixir terms as `actual state = desired state` in that the action will try to make the left true. Take templating for example, we may say that our desired state is `/some/file (contents: "foo")`, the DSL will make a comparison to the state on the machine, which will see `nil = /some/file (contents: "foo")` then try to make the left true by sending a file with the contents to /some/file. If the file exists but the contents are different, we may see `/some/file (contents: "bar") = /some/file (contents: "foo")` in the DSL's comparison, in which it can simply change the contents. The file mode might be different in whilch the action can simply chmod the file. What actions do not do, is compare two files and blindly throw a new file. A file action does not specify throwing a file over a new file but how to get the file to look like the desired file.

This may get more confusing with other use cases outside of systems configuration. For example, scheduled tasks. But the same logic applies in that `task ran 1 hour ago = task queued to run` is also a valid assertion, and the DSL will run another task to make that statement true. It can however make it easier to readson with provisioning, where we might say `3 servers exist with this golden image` and if one server gets accidentally deleted, the provisioner will see the `2 = 3` and provision another server.

This leads to a more powerful way of describing infrastructure, as not only do the scripts describe how to get to a desired state, but to keep that state, creating options for self healing infrastructure as well as monitoring.
